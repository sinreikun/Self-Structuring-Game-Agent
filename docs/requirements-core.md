# 最小I/O自己発達型ゲームAI ― 完成版開発指示

あなたはこのプロジェクトの主任ソフトウェアエンジニアです。

以下の思想・制約・完成条件に従い、単なる試作品ではなく、長時間単独稼働できる完成形を目標としてアプリケーションを設計・実装してください。

最重要なのは「最初から強いゲームAIを作ること」ではありません。

**画面と限定された入力しか知らないAIを未知のゲームへ置き、大量の試行錯誤から、ゲームを理解するための概念・技能・観測方法・分析器・自己改善方法そのものを自律的に獲得させるための実験環境を作ること**が目的です。


# 1. プロジェクトの基本思想

人間がゲーム固有の攻略ロジックを実装してはいけません。

AIへ最初から与えてよいゲーム側の情報は、原則として以下だけです。

- 対象ゲームの画面を取得する能力
- 入力可能なキー・ボタンの一覧
- 許可された入力を対象ゲームへ送信する能力
- キーの押下時間を指定する能力
- 全入力を解放する能力
- 対象ゲームを起動・終了・再起動する能力
- 対象ウィンドウを再検出・再接続する能力
- 再度ゲーム画面を取得する能力
- 経験を保存するストレージ
- ローカルLLMを呼び出す能力
- AI自身の作業領域内でコードを生成・変更・実行する能力
- 十分な計算時間

AIへゲーム固有の意味を最初から教えてはいけません。

例：

- HP
- 敵
- アイテム
- 階段
- マップ
- プレイヤーキャラクター
- カーソル
- メニュー
- 死亡
- 攻撃
- 移動
- ダンジョン
- 装備
- 満腹度
- 特定キーの意味
- 攻略上の正解

これらに相当する概念を必要に応じてAI自身が経験から形成することを目的とします。


# 2. 完成版の最重要条件

初回設定後、人間が継続的に面倒を見る必要がないことを完成条件とします。

初回に人間が設定するものは原則として以下だけです。

- 対象ゲームの実行ファイル
- 対象ゲームウィンドウ
- ゲームへ送信可能なキー・入力一覧
- ローカルLLM接続設定
- AIの作業フォルダ
- データ保存容量上限
- 必要であればゲーム起動オプション

以後は、

1. ゲーム起動
2. ウィンドウ検出
3. LLM接続
4. 観測開始
5. 入力実験
6. 経験保存
7. 経験分析
8. 仮説形成
9. 問題発見
10. 改善案生成
11. 解析器・内部機構・コードの生成または変更
12. Sandbox評価
13. 過去経験での比較評価
14. 短期実機A/B評価
15. 改善版の自動採用または棄却
16. 問題発生時のロールバック
17. 自律運転継続

まで、人間の追加作業なしで実行できる構造にしてください。


# 3. 人間がやらないこと

以下を人間の継続作業にしてはいけません。

- 敵認識器を人間が追加する
- HUD領域を人間が指定する
- OCR領域を人間が調整する
- HPの意味を人間が教える
- マップの見方を人間が教える
- アイテム認識を人間が実装する
- キーの意味を人間が教える
- メニュー操作を人間が登録する
- 死亡画面を人間が登録する
- 復帰方法を人間が登録する
- 戦闘戦術を人間が追加する
- ゲーム固有のExecutorを追加する
- 認識失敗のたびに人間がコードを修正する
- AIが迷うたびに人間がプロンプトを追加する
- 自己改造のたびに人間へ承認を求める

問題が発生した場合は、

「人間に新しい専用機構を作ってもらう」

のではなく、

「なぜ現在のAIではその問題を発見・分析・改善できなかったのか」

をAI側が研究対象にできる構造としてください。


# 4. システムを2領域に分離する

## A. Host / Experimental Infrastructure

この領域は実験装置です。

AI自身には原則として書き換えさせません。

責務：

- ゲームプロセス管理
- ゲームウィンドウ検出
- 画面取得
- 入力送信
- 入力許可リスト管理
- 全キー解放
- ゲーム再起動
- AIプロセス監視
- LLM接続
- ファイルアクセス制限
- スナップショット
- 世代管理
- ロールバック
- ストレージ容量管理
- 診断情報保存
- 自律Runtimeの起動
- Runtime起動失敗時の旧安定版復旧

Hostはゲームの意味を持ってはいけません。

「敵」「HP」「マップ」「死亡」などをHost側へ実装してはいけません。


## B. Agent / Self-Modifiable Runtime

こちらが研究対象です。

指定したAgent Root以下について、AI自身に以下を許可してください。

- 読み取り
- 書き込み
- 新規ファイル作成
- ファイル削除
- ディレクトリ作成
- 自分のプログラム変更
- 補助解析器生成
- データベース生成
- モデル生成
- テスト生成
- 自作ツール実行
- 自分自身の内部アーキテクチャ変更

Agent Root外への書き込みは禁止してください。

ゲーム本体のファイル変更も禁止してください。


# 5. Bootstrapは保護する

AIが自己改造に失敗して完全停止しないよう、HostとAgent Runtimeの間に最小Bootstrapを設けてください。

Bootstrapの責務は原則として以下だけです。

- 現在のActive Revision確認
- Runtime起動
- 起動成功確認
- 一定時間内に正常起動しない場合の失敗判定
- 前の安定Revisionへの自動ロールバック
- 再起動

BootstrapそのものはAgentから変更不可としてください。


# 6. 初期アーキテクチャ

初期実装として以下の役割を持たせて構いません。

ただし、これを永久固定のアーキテクチャにはしないでください。

## Player

高速な現場操作担当。

責務：

- 最新画面取得
- 現在利用可能な軽量分析を使用
- 入力候補選択
- 1回または短い操作列を実行
- 前後状態保存
- 次の操作へ進む

長いLLM推論を毎手待たないこと。

大量の経験を生成することを優先します。


## Experience Store

一次経験を保存します。

最重要原則：

**生の経験を失わないこと。**

最低限保存する情報：

- 入力前画面
- 実際に送った入力
- 押下時間
- 入力時刻
- 入力後画面
- 観測時刻
- セッションID
- ゲームプロセスIDまたは再起動世代
- Agent Revision
- 使用した解析器Revision
- Raw Evidenceへの参照

後から解析器が改善した場合、過去の生データを再解析できるようにしてください。


## Scientist

Playerと非同期に動作します。

責務：

- 経験比較
- 反復パターン発見
- 相関発見
- 因果候補形成
- 未知の列挙
- 矛盾検出
- 誤った仮説の反証
- 失敗分類
- 新しい検証課題生成
- 現在の観測方法の不足検出
- 現在の内部構造の不足検出
- Engineerへの改善課題提示

Scientist自身はゲームを直接操作しない設計を初期形としてください。


## Engineer

Scientistが見つけた問題を解決する内部機構を設計します。

生成・変更対象の例：

- 画像比較器
- 領域検出器
- 物体候補追跡器
- OCR前処理
- OCR利用判断
- 状態表現
- 経験検索器
- パターン分類器
- 技能抽出器
- 予測器
- キャッシュ
- インデックス
- 行動選択器
- 実験生成器
- 自己診断器

特定ゲーム専用の意味ラベルを最初から与えてはいけません。


## Evaluator / Sandbox

Engineerが生成した変更を本番へ直接入れてはいけません。

必ず、

改善案
→ Candidate Revision
→ Sandbox
→ Replay Test
→ Regression Test
→ 必要なら実機短期A/B
→ 自動評価
→ 採用または棄却

という流れを通してください。


# 7. 初期役割そのものも将来的には変更可能

Player / Scientist / Engineer / Evaluatorという分類は、人間が理解しやすい初期構造として使用して構いません。

ただしAgentが経験を積んだ結果、

- 分割方法が非効率
- 新しい役割が必要
- 二つの役割を統合したほうがよい
- 新しい内部処理層が必要

などを発見した場合は、Agent自身の可変領域内で内部アーキテクチャを変更できる設計にしてください。


# 8. 観測・推論・仮説を分離する

内部知識では必ず、

- 観測事実
- 行動経験
- 推論
- 仮説
- 一般化された概念

を区別してください。

例：

観測：
「画面上のある領域に反復する表示がある」

経験：
「特定の画面イベント後、その領域が変化した」

仮説：
「この領域は何らかの状態量を表している可能性がある」

概念：
「この値を一定条件に保つことが長時間継続と相関する」

これらを同一の「事実」として扱ってはいけません。


# 9. unknownを正式な状態にする

分からない場合はunknownとしてください。

既存ゲーム知識やLLMの事前知識から意味を勝手に補完しないでください。

意味不明な画面、認識不能な文字、因果不明な変化を、推測だけで確定しないでください。


# 10. Provenanceを保持する

すべての知識へ出所情報を保持してください。

最低限：

- observed
- action_experience
- inferred
- self_generated_model
- external
- human_provided

検証状態も保持してください。

最低限：

- unknown
- hypothesis
- supported
- reproduced
- disputed
- refuted

外部情報と自力発見を混ぜないでください。


# 11. Newbornモード

完全新規実験を作れるようにしてください。

Newbornでは、

- 学習済みゲーム固有知識なし
- 外部攻略情報なし
- 人間ラベルなし
- 過去ゲーム固有経験なし
- 過去ゲーム固有解析器なし

とします。

保持してよいものは、

- 観測方法を改善する能力
- 仮説検証能力
- 経験管理能力
- 自己改善能力
- 一般的な因果推論能力

など、ゲーム非依存のメタ能力だけです。


# 12. Experiencedモード

同一ゲームで自力獲得した、

- 経験
- 仮説
- 概念
- 技能
- 自作解析器
- 自己改善結果

を引き継げるモードを用意してください。


# 13. Guidedモード

比較研究用として、人間知識または外部情報を許可するモードも設けて構いません。

ただしNewbornとはデータ・Provenanceを完全に区別してください。


# 14. 「自分」の発見もAIに任せる

人間側からプレイヤーキャラクターの場所や意味を教えないでください。

AIが、

- 入力と同期して変化する対象
- 多数の画面で継続して存在する対象
- 周辺変化と特殊な相関を持つ対象

などから、自分に相当する対象を発見できるかを研究対象とします。

内部名が「self」である必要もありません。


# 15. OCRを中心に設計しない

文字を読むことと画面を理解することを同一視しないでください。

最初から毎フレームOCRする方式は禁止します。

以下のような情報も利用可能です。

- 画像差分
- 色
- 輝度
- エッジ
- 形
- 領域
- 動き
- 入力との同期
- 位置関係
- 再出現
- 時系列変化

OCRが必要だとAI自身が判断した場合に追加解析器として利用できるようにします。


# 16. 観測方法そのものを自己改善対象にする

画面取得方法を一種類に固定しないでください。

Agentは必要に応じて、

- 全画面解析
- 一部分の切り抜き
- 前後フレーム比較
- 差分抽出
- 高密度観測
- 低密度観測
- キャッシュ利用
- 再観測
- 特定領域追跡

などを自ら設計できるようにしてください。


# 17. 速度も自己調整する

固定待機時間・固定FPSを最終仕様にしないでください。

以下を観察しながら速度を変えられるようにしてください。

- 入力後の画面安定
- 予測一致率
- 再観測率
- 認識品質
- フレーム取りこぼし
- 入力結果unknown率
- CPU/GPU負荷
- LLM待機時間
- ストレージ書き込み負荷

既知状態では高速化し、未知状態や重要遷移では観測密度を上げることを自律的に学習可能にしてください。


# 18. AI自身の実行効率も改善対象

ゲーム攻略だけでなく、自身の処理効率も自己改善対象にしてください。

例：

- 同じ画像を何度も解析している
- LLM呼び出しが多すぎる
- CPU処理がボトルネック
- DB検索が遅い
- 保存形式が非効率
- 不要な解析を毎フレーム実行している

これらをScientist / Engineerが自律的に検出・改善できる構造にしてください。


# 19. LLMを一手ごとの必須クリティカルパスにしない

毎入力ごとに大型LLM応答を待つ設計は禁止します。

高速Playerと、低速な分析・研究・自己改善層を非同期に動かしてください。

LLMは、

- 高度分析
- 仮説整理
- 改善設計
- コード生成
- Knowledge Book生成
- 重要な未知状態の分析

など、必要な場面で使用してください。


# 20. 自動自己改造

AI自身のコード変更について、人間承認を毎回要求してはいけません。

Candidate Revisionを自動生成し、

- 起動確認
- 基本テスト
- Replay評価
- Regression評価
- 処理性能比較
- unknown率比較
- 予測性能比較
- 過去成功例の破壊確認
- 必要なら短時間実機A/B

を行い、自動採用・自動棄却してください。


# 21. 自己改造失敗から自動復旧

最低限、

- 全Revision保存
- Active Revision管理
- Last Known Good管理
- 起動失敗検知
- Runtimeクラッシュ検知
- 自動ロールバック
- 自動再起動

を実装してください。

AI自身が自分を壊した場合でも、人間が手作業でコードを戻さなくて済むことを完成条件とします。


# 22. ゲーム復旧

AIがゲーム内で操作不能になった場合、まず自身が学習した復旧方法を試して構いません。

ただし復旧試行は必ず有限回にしてください。

一定条件を超えた場合、Hostが強制的にゲームプロセスを再起動できるようにしてください。

無限復旧ループは禁止です。


# 23. 永続化

以下はアプリ・LLM・PCの再起動後も復旧可能にしてください。

- 現在セッション
- 現在Revision
- 安定Revision
- Active Experiment
- Pending Job
- Knowledge State
- Experience Store位置
- 自作解析器
- 仮説
- 技能
- 自己改造履歴

PC再起動後も「前回の続き」から自律再開できる構造を目標としてください。


# 24. ストレージ管理

生画像を重要な一次Evidenceとして扱います。

ただしストレージ容量は有限なので、ユーザーが保存容量上限を設定できるようにしてください。

ストレージ管理自体は自動で行ってください。

優先保存対象：

- 重要Evidence
- 新規未知状態
- 自己改造評価に利用したEvidence
- 失敗事例
- 仮説の根拠
- 仮説を反証した根拠
- 重要な状態遷移

既知状態の大量反復データは、安全な方法で圧縮・集約できる設計を検討してください。

ただし意味のある一次Evidenceを勝手に不可逆削除しないよう注意してください。


# 25. 人間への質問を問題解決手段にしない

AIが分からないことを見つけても、

「人間に聞く」

を通常の解決方法にしないでください。

例：

悪い挙動：
「この数字の意味を教えてください」

良い挙動：
「意味不明な変数候補を発見」
→ 過去経験検索
→ 変化条件抽出
→ 複数仮説生成
→ 仮説を区別可能な実験を設計
→ 実験依頼
→ 再評価

人間が呼ばれるのは実験装置外の問題だけにしてください。


# 26. 人間の介入が許される異常

例：

- ゲーム実行ファイルが消失
- LLMサーバーが長時間利用不能
- ディスク故障
- Host自身の故障
- 対象ゲームがインストールされていない
- 対象ウィンドウが生成されない
- OS権限異常
- 保存領域を確保不能
- ハードウェア障害

以下では人間を呼ばないでください。

- 敵らしき対象に勝てない
- 画面が理解できない
- メニューから戻れない
- 文字が読めない
- キーの意味が分からない
- 死亡した
- 何度も同じ失敗をする

これらは研究対象です。


# 27. 人間向けUIの最重要原則

人間に通常見せる情報は、原則として以下だけにしてください。

- 日本語
- ゲーム画面
- スクリーンショット
- 切り抜き画像
- 比較画像
- 差分画像
- 注釈画像
- グラフ
- 図
- 表
- 一般的な数値

人間が内部実装を解読しなければ理解できない表示を通常UIへ混ぜないでください。


# 28. 通常UIにコードを混ぜない

以下は通常UI・Knowledge Book・自己改良報告・警告・復旧報告へ原則として表示しないでください。

- ソースコード
- JSON
- Python断片
- コマンドライン
- スタックトレース
- 内部API名
- クラス名
- 関数名
- 生のファイルパス
- 機械向け識別子
- 内部データ構造

必要な場合は日本語へ翻訳してください。

例：

悪い表示：
「region_tracker_v17 confidence=0.84」

良い表示：
「追跡中の画面領域。現在の確信度は高めです。」

ただし研究上意味のある数値、

- 成功率
- 予測精度
- 再現回数
- 処理時間
- unknown率
- 仮説件数

などはそのまま表示して構いません。


# 29. 開発者詳細

コードや内部ログは削除する必要はありません。

完全に保存してください。

ただし通常画面から分離し、

「開発者詳細」

を明示的に開いた場合だけ表示する構造にしてください。

開発者詳細では、

- ソースコード
- 差分
- JSON
- 生ログ
- スタックトレース
- ファイル情報
- 内部ID

などを確認可能にしてください。


# 30. 自己改良報告

Agentが自己改造した場合、人間には日本語で以下を報告してください。

- 何を変更したか
- なぜ変更したか
- 何を根拠に問題だと判断したか
- どのように評価したか
- 改善した指標
- 悪化した指標
- 採用したか棄却したか

コードそのものは通常表示しないでください。


# 31. エラー表示

通常画面へ生スタックトレースを表示しないでください。

例：

「内部処理で問題が発生しました。
直前の安定版へ自動復旧しました。
ゲームプレイを再開しました。」

のように表示してください。

技術的な完全ログは内部に保存してください。


# 32. 画像による説明

視覚に関する発見は、可能な限り画像で説明してください。

例：

- 注目している領域を枠表示
- 入力前と入力後を並べる
- 同一対象候補を時系列で並べる
- 変化部分を強調表示
- AIが重要だと考えた場所を可視化

人間がAIの認識過程を直感的に追えることを重視してください。


# 33. Knowledge Book

AI内部の構造化知識から、人間が読める研究ノートを自動生成してください。

Knowledge Book自体をAIの一次記憶にはしないでください。

最低限、人間向けに以下を日本語で確認可能にしてください。

- 発見した画面領域
- 入力について分かったこと
- 持続する対象候補
- 自分に相当する対象候補
- 状態変数候補
- 空間についての仮説
- 危険についての仮説
- 獲得した技能
- 支持された仮説
- 反証された仮説
- 現在の未知
- 次に行おうとしている実験
- 自分で追加した解析方法
- 解析方法の有効性
- 自己改造履歴

可能なら根拠画像も付けてください。


# 34. GUI

通常利用時に必要な主要操作はできるだけ以下へ限定してください。

- START
- PAUSE
- STOP
- NEWBORN
- EXPORT

初期設定画面は別途用意して構いません。

通常画面では最低限、

- 稼働状態
- 対象ゲーム
- 稼働時間
- 現在のAI世代
- ゲーム画面
- 現在の活動内容
- 現在の実験
- 発見数
- 仮説数
- 支持済み仮説数
- 反証数
- 技能数
- 自己改良回数
- 最近の自己改良
- 最近の重要発見

を日本語で観察できるようにしてください。


# 35. 評価をゲームクリアだけにしない

評価項目には少なくとも以下を含めてください。

## 発見能力

- 未知の規則を発見できたか
- 独立経験で再確認できたか
- 誤った仮説を自己反証できたか

## 予測能力

- 次画面予測
- 状態変化予測
- 入力効果予測
- 長期結果予測

## 概念形成

- 同一対象をまとめられるか
- 対象と状態を区別できるか
- 一時特徴と恒常特徴を区別できるか
- 自己・危険・資源・場所などに相当する抽象概念が形成されるか

## 自己改善

- 自分の観測不足を発見できるか
- 新しい解析方法を提案できるか
- 実装できるか
- 評価できるか
- 改善版だけを採用できるか
- 不要な解析方法を捨てられるか
- 速度と精度を調整できるか
- 自己改造失敗から復旧できるか


# 36. 失敗を削除しない

以下も重要な研究データです。

- 死亡
- 無限ループ
- メニュー迷子
- 誤認
- 誤った因果推論
- 過剰一般化
- 古い知識の誤適用
- 認識器改悪
- 自己改造失敗
- 高速化による観測失敗

可能であれば、

- その時点で何を信じていたか
- なぜその判断をしたか
- 後から何が間違いだと分かったか

まで追跡可能にしてください。


# 37. 人間向け出力と内部データを分離する

内部では機械処理に適した形式を自由に使って構いません。

例：

- SQLite
- JSON
- バイナリ
- ベクトルデータ
- 画像
- 構造化イベント
- ログ

ただし人間向けUIはPresentation Layerを通し、日本語・画像・図表中心に変換してください。

内部表現をそのまま人間へ露出させないでください。


# 38. 診断機能

問題調査用として診断情報を一括Exportできるようにしてください。

ただし通常利用者にログ解析を要求してはいけません。

Exportには必要に応じて、

- 設定
- Hostログ
- Agentログ
- Revision情報
- エラー情報
- Knowledge Book
- 最近のEvidence
- 自己改造履歴
- 性能履歴

などを含めてください。


# 39. セキュリティ境界

Agentには対象ゲームを操作するために必要な能力と、自分のAgent Root以下を編集する能力のみを与えてください。

原則禁止：

- OS全体への任意書き込み
- Windowsシステムファイル変更
- Agent Root外の任意ファイル変更
- ゲーム本体改造
- レジストリ変更
- 他アプリの任意操作
- 無許可ネットワークアクセス
- 入力許可リスト外のキー操作

Host側で技術的に強制してください。

「プロンプトで禁止しただけ」にしないでください。


# 40. 実装方針

いきなり巨大な万能システムを一括生成しないでください。

ただし最終仕様を削って簡単なデモで終わらせてもいけません。

最終完成形を見据えた上で、段階的に実装してください。

推奨順：

Phase 0
Host・Capture・Input・Restart・Storage・Replay・Versioning・Watchdog

Phase 1
Experience Eventと高速Player

Phase 2
非同期Scientist

Phase 3
仮説・Provenance・Validation

Phase 4
EngineerとCandidate Revision生成

Phase 5
Sandbox / Replay / Regression評価

Phase 6
自動昇格・ロールバック

Phase 7
Knowledge Book・GUI・画像注釈

Phase 8
Newborn / Experienced / Guided

Phase 9
長時間自律運転・復旧・永続化

Phase 10
別ゲームへの転移実験


# 41. 開発中の判断原則

実装中に機能不足を発見した場合、まず次を考えてください。

「この機能を人間が直接追加すると、実験対象であるAI自身の発見機会を奪わないか？」

ゲーム固有知識なら原則として追加しないでください。

一方で、

- 安全なファイル操作
- プロセス監視
- 生データ保存
- Sandbox
- Versioning
- Rollback
- Replay
- 非同期処理
- 診断
- UI

など、ゲームの意味を教えない汎用実験装置は人間側で実装して構いません。


# 42. 実装時の作業姿勢

既存リポジトリがある場合は、最初に全体を調査してください。

その後、

1. 現状構造を把握
2. 今回の思想と衝突する既存仕様を抽出
3. Host固定領域とAgent可変領域を設計
4. データ構造を設計
5. 自律復旧構造を設計
6. 段階的に実装
7. 自動テスト
8. 実行確認
9. ドキュメント更新

まで進めてください。

小さな判断ごとに人間へ質問しないでください。

情報不足でも安全に決められる項目は、プロジェクト思想に沿って妥当な判断を行ってください。

本当に外部情報がないと進行不能な場合のみ質問してください。


# 43. 人間が読むドキュメント

READMEや操作説明も日本語を基本としてください。

利用者がプログラムコードを理解していなくても、

- セットアップ
- 初回設定
- START
- PAUSE
- STOP
- NEWBORN
- EXPORT
- 現在何をしているか
- 問題が起きた時に人間が対応すべきか否か

を理解できるようにしてください。

専門用語が必要な場合は日本語で説明してください。


# 44. 完成判定

最低限、次をすべて満たした時点を「完成版」と考えてください。

- 初回設定だけで長時間単独稼働できる
- ゲーム固有知識なしで開始できる
- 画面・入力・再起動だけから経験を生成できる
- 生Evidenceを保持する
- 仮説と事実を区別できる
- unknownを扱える
- Playerが高速に経験を蓄積できる
- Scientistが非同期分析できる
- 自身の不足能力を問題として発見できる
- Engineerが改善案を実装できる
- Sandboxで自己改造を評価できる
- 改善版を自動採用できる
- 改悪版を自動棄却できる
- 自己破壊から自動ロールバックできる
- ゲーム異常から有限回で復旧できる
- PCやアプリ再起動後に継続できる
- ストレージを自動管理できる
- 通常運用で人間への質問を必要としない
- 人間向け情報が日本語・画像・図表中心である
- 通常画面に不要なコードを表示しない
- Knowledge Bookを自動生成できる
- Newborn個体を作成できる
- ゲーム固有知識と汎用メタ能力を分離できる


# 45. 最終原則

このプロジェクトで作るのは、

**「人間が設計した攻略方法をLLMに実行させるゲームAI」ではありません。**

作るのは、

**「未知のゲームへ投入されたAIが、自分に何が足りないかを発見し、観測・実験・分析・仮説形成・技能獲得・解析器生成・自己改造・評価・失敗・復旧を繰り返しながら、自分自身をゲームを理解できる存在へ変えていくための自律研究環境」**

です。

迷った場合は、

**「それは人間がゲームの意味を教えてしまっていないか？」**

**「人間が継続的に世話をしないと動かない構造になっていないか？」**

**「AI自身が問題を発見し、改善する機会を奪っていないか？」**

の3点へ戻って判断してください。


# 46. 最初に行うこと

この指示を受けたら、いきなり断片コードだけを提示しないでください。

まず現在のリポジトリがある場合は調査し、ない場合は新規プロジェクトとして設計してください。

そのうえで、

- 最終アーキテクチャ
- Host固定領域
- Agent可変領域
- データ保存構造
- 自己改造・評価・昇格・ロールバックの流れ
- GUI構成
- 開発フェーズ
- 完成条件

がこの仕様と矛盾していないことを確認してから実装へ進んでください。

実装開始後は、可能な範囲で自律的に作業を進め、ビルド・テスト・修正まで実施してください。

一部分だけ作って「残りは今後実装」として止めることを最終成果にはしないでください。

最終的には、初回設定から自律運転開始まで実際に操作できる状態を目標にしてください。
