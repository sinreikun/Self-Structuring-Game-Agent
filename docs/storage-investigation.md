# 容量消費の調査と保持設計

## 確認できたこと

改善前のv0.1.0-dev.4は、入力の前後に原寸PNGを保存し、完全一致のPNGだけ内容ハッシュで共有する。動く画面や微細な描画変化では新しいPNGが増え続ける。古い反復のGCはなく、作業フォルダ全体（モデル、エンジン、圧縮アーカイブ、以前の個体、画像、DB等）を同じ上限へ計上し、reserve失敗で停止する。研究は通常100経験を待って開始するため、初期の画像保存と研究開始の容量予算が連携していなかった。

今回の添付は改善指示であり、10GiBを使い切った時の完全な使用量一覧ではない。以前に提出された研究記録も、今回の容量超過時点の内訳を証明しない。そのため「何GiBがどの種類だったか」は断定しない。

参考として1枚6MiBの完全不一致画像なら、入力前後100経験で約1.17GiBを消費する。これだけで10GiBになるとは限らず、モデル、古い資産、以前の個体等の占有が重要である。新しい診断はmodels / engine_runtime / engine_archives / evidence_images / database_and_wal / agent_files / checkpoint_cache / exports等を別々に計上する。

## 保持区分

| 区分 | 判断根拠 | 方針 |
| --- | --- | --- |
| 永続 | Knowledgeの根拠ID、評価結果の経験ID、明示pin、異常・復旧前後、コード世代・設定・報告 | 自動削除しない |
| 高価値の経験 | 直近のReplay窓、初期の遷移代表例、予測逸脱、現在の研究・比較 | 件数による保持と研究中のpin |
| 整理対象 | 保持期間・件数を過ぎ、永続参照のない経験、未参照画像、期限切れの部分ダウンロード、古いアプリ本体 | 統計へ集約、参照解除後の画像回収、再生成可能物の整理 |

近似画像を似ているという理由で置換しない。統計の条件には完全一致の前後ハッシュ、特徴、入力、押下時間、Agent revision、process generation、予測・変化を分けて残す。画像が残らない集約経験を、原画像があるReplay根拠として利用しない。

80/90/95/98%の段階を持ち、通常画像やAgent作業要求は最後の5%を使わない。容量警告時には通常の研究間隔を短縮する。GCは小分けで進め、DBの参照解除をコミットしてからファイルを消す。途中で削除に失敗した画像は次回へ残し、DBを既に消した画像への参照へ巻き戻さない。小画像が4096経験を超えた場合も事前整理する。

## 限界

永続保護データだけで容量を使い切れば、安全停止が必要になる。上限がある中で永久保持と無制限運転の両方は保証しない。個体をまたぐ過去データの自動削除は行わず、現在の実験の経験・キャッシュを整理する。Newbornで過去個体の知識を読み込んで整理判断や学習へ流用しない。

10GiBの会計試験では疎ファイルを資産に見立てる。画像GCは小容量の実保存試験で確認する。実ゲームでの何日もの運転や、10GiBの実データ書き込みを完了したという意味ではない。
