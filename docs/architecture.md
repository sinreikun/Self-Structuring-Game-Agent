# 設計と検証境界

## 固定領域

Host・Bootstrap・GUI・配布物検証器はアプリケーションに同梱する。Hostはウィンドウの所有PIDと前面状態を入力ごとに照合し、許可した通常キーだけを送る。画面や入力へゲームの意味は付けない。

## 可変領域

AgentはWebAssemblyで動く。生成コードへOS、WASI、ネットワーク、プロセス、ネイティブDLLを公開しない。燃料・メモリ・スタックを制限する。Agent Rootの変更要求はHostがパス・シンボリックリンク・容量を検証する。Agent自身のモジュール、作業ファイル、モデル、知識をHost公式更新と分ける。

初期ABIは画面の縮小輝度配列をメモリへ渡し、入力選択・押下時間・観測間隔・変化予測を返す。メモリ上の内部構造、関数分割、独自解析を変更できる。LLMは非同期Scientist/Engineerで使い、一手の待ち時間へ含めない。初期モジュールはゲーム非依存の探索を行う。

## 保存構造

ユーザー保存先直下にhost（設定・SQLite・ジョブ・セッション）、evidence（内容ハッシュ付きPNG）、agents/個体/revisions（不変のコード世代）、assets（engine/model/library別）、updates、exportsを分離する。観測・経験・仮説・概念・技能は出所と検証状態、根拠IDを持つ。Newbornでは新規DBと個体を作り、過去のゲーム知識を渡さない。

SQLiteはWALとトランザクションを用いる。画面は先に原子的保存し、経験は入力予定を永続化してから送信する。不完全な操作は再起動時に中断として記録し、再送しない。容量不足時はEvidenceを消さず停止する。重複PNGは内容で共有する。

## 自己改善

問題の発見 → 永続ジョブ → LLMの構造化提案 → WAT候補 → 有限Sandbox → 時間分割したReplayと保持済み成功例のRegression → 必要な実機交互A/B → Hostが算出した指標による採否 → 起動確認 → Active更新。

評価器の判定とLLMの自己申告は分離する。入力効果は画像変化の有無から評価し、攻略成功と同一視しない。比較不能・サンプル不足は採用しない。Active異常時は直前安定世代へ戻し、入力を全解放する。すべての候補・評価・失敗は残す。

## UI

初回設定、モデル選択、監視画面、研究ノート、自己改善履歴、開発者詳細を分ける。通常画面は日本語、画像、数値を使い、生コードと内部ログは開発者詳細だけに出す。START/PAUSE/STOP/NEWBORN/EXPORTを主要操作とする。

## 配布と開発フェーズ

Windows CIでPythonと依存を単一EXEへ同梱する。LLMエンジン・モデルは署名付きカタログから容量制限とSHA-256検証付きで取得する。公式更新は別Helperへ引き継ぎ、起動確認失敗時に戻す。

Phase 0–3: 固定I/O・保存・探索・非同期研究と出所。
Phase 4–6: 候補生成・隔離評価・昇格・復旧。
Phase 7–9: 日本語UI・ノート・個体分離・継続運転。
Phase 10: Windows実機で複数ゲーム・長時間・障害注入・配布復元を検証する。

## 完成条件

添付原文をrequirements-core.mdとrequirements-distribution.mdに保存。自動テストだけで未知ゲーム理解や長期安定性の完成を宣言しない。Windowsの画面取得、フォーカス喪失時の解放、クラッシュ復旧、実モデル推論、自動導入、署名済み実配布元、EXE更新の実機検証を必要条件とする。Linuxで通ったテストとWindows未検証を明確に区別する。
