# 設計と検証境界

## 固定領域

Host・Bootstrap・GUI・配布物検証器はアプリケーションに同梱する。Hostはウィンドウの所有PIDを入力ごとに照合し、許可した通常キーを対象ウィンドウへのメッセージとして送る。前面状態・ユーザーの操作では停止しない。全体入力・フォーカスの強制取得は行わない。画面や入力へゲームの意味は付けない。

画面は専用の固定WorkerでPrintWindowにより対象ウィンドウから取得する。背面や他アプリに覆われた状態でも、デスクトップの表示画素を代用しない。描画処理が応答しない場合は期限内にWorkerを終了し、Hostの監視・入力解放を継続する。最小化中は待機し、復元後に継続する。Raw Input専用などメッセージ入力を受けないゲームは自動的な全体入力に切り替えず、非対応として扱う。

## 可変領域

AgentはWebAssemblyで動く。生成コードへOS、WASI、ネットワーク、プロセス、ネイティブDLLを公開しない。燃料・メモリ・スタックを制限する。Agent Rootの変更要求はHostがパス・シンボリックリンク・容量を検証する。Agent自身のモジュール、作業ファイル、モデル、知識をHost公式更新と分ける。

初期ABIは画面の縮小輝度配列をメモリへ渡し、入力選択・押下時間・観測間隔・変化予測を返す。メモリ上の内部構造、関数分割、独自解析を変更できる。LLMは非同期Scientist/Engineerで使い、一手の待ち時間へ含めない。初期モジュールはゲーム非依存の探索を行う。

## 保存構造

ユーザー保存先直下にhost（設定・SQLite・ジョブ・セッション）、evidence（内容ハッシュ付きPNG）、agents/個体/revisions（不変のコード世代）、assets（engine/model/library別）、updates、exportsを分離する。観測・経験・仮説・概念・技能は出所と検証状態、根拠IDを持つ。Newbornでは新規DBと個体を作り、過去のゲーム知識を渡さない。

SQLiteはWALとトランザクションを用いる。画面は先に原子的保存し、経験は入力予定を永続化してから送信する。不完全な操作は再起動時に中断として記録し、再送しない。重複PNGは内容で共有する。80/90/95/98%の段階的GCと5%の緊急予約枠を持つ。永続根拠はpinとKnowledge参照で保護し、最新128件・代表遷移・予測逸脱例を保持する。古い未参照の反復は統計へ集約し、その画像だけを削除する。保護対象で容量が満たされた時だけ停止する。

## 自己改善

問題の発見 → 永続ジョブ → LLMの構造化提案 → WAT候補 → 有限Sandbox → 時間分割したReplayと保持済み成功例のRegression → 必要な実機交互A/B → Hostが算出した指標による採否 → 起動確認 → Active更新。

評価器の判定とLLMの自己申告は分離する。入力効果は画像変化の有無から評価し、攻略成功と同一視しない。比較不能・サンプル不足は採用しない。Active異常時は直前安定世代へ戻し、入力を全解放する。すべての候補・評価・失敗は残す。

## UI

初回設定、モデル選択、監視画面、研究ノート、自己改善履歴、開発者詳細を分ける。通常画面は日本語、画像、数値を使い、生コードと内部ログは開発者詳細だけに出す。START/PAUSE/STOP/NEWBORN/EXPORTを主要操作とする。

## 配布と開発フェーズ

Windows CIでPythonと依存を単一EXEへ同梱する。LLMエンジン・モデルは署名付きカタログから容量制限とSHA-256検証付きで取得する。本体と固定Launcherを分け、署名付きManifestから本体を並存配置する。起動確認失敗時にlast-known-goodへ戻す。旧版の上書き型Helperは互換用に残すが通常導線からは呼ばない。

Phase 0–3: 固定I/O・保存・探索・非同期研究と出所。
Phase 4–6: 候補生成・隔離評価・昇格・復旧。
Phase 7–9: 日本語UI・ノート・個体分離・継続運転。
Phase 10: Windows実機で複数ゲーム・長時間・障害注入・配布復元を検証する。

## 完成条件

添付原文をrequirements-core.mdとrequirements-distribution.mdに保存。自動テストだけで未知ゲーム理解や長期安定性の完成を宣言しない。Windowsの背面画面取得、対象ウィンドウだけへの入力、前面切り替え時の継続、クラッシュ復旧、実モデル推論、自動導入、署名済み実配布元、EXE更新の実機検証を必要条件とする。Linuxで通ったテストとWindows未検証を明確に区別する。

## 活動・診断・配置

Controller/Scientistはfrozen RealtimeActivityをロック内で置換し、GUIへ読み取り専用snapshotを渡す。GUIは生のDB全体を毎回読み出さず、バックグラウンドの集計スナップショットと直近イベントを読む。画像は更新・表示方式・サイズ・注目領域が変わった時だけ描画する。推論ランプはLocalLLM.completeの実呼び出しを囲む。

診断は最大24MiBの入力予算を持つallowlist exporter。SQLiteは稼働DBをロックして必要行だけ別DBへ束縛パラメータで複写し、文字列中の秘密・パスを除外する。これは全DBの復元用バックアップではない。未知のAgent作業ファイルや環境変数は収集しない。

Layout schema=1は安定UI IDごとにwindow/pane/notebook/panel状態を保持する。未知ID・壊れた値は無視、未登録要素はデフォルト。負座標モニタも扱い、画面外の保存位置は現在の表示領域へ補正する。ゲームやAgentの意味ラベルはUIの都合で追加しない。

GCは1回につき最大512経験・128画像の小分け処理とする。小画像の経験が4096件を超えた場合は、容量が80%未満でも整理を進める。統計には完全一致の前後画像ハッシュ・特徴・入力・押下時間・実行世代・プロセス世代・予測・変化を分けて残し、異なる条件を混ぜない。容量警告時は研究間隔を前倒しする。未確認の画像変化を成功や失敗へ読み替えない。
