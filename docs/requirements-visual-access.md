# SelfStruct 視覚アクセス権限・汎用視覚研究機構 改善指示

現在のSelfStructでは、Agent / Scientistがゲーム画面から得られる情報が狭く、画面変化量や縮小輝度画像などに強く依存しています。

これを改善し、

**Visionモデルか非Visionモデルかに関係なく、SelfStructに標準装備された「目」へ自由にアクセスし、その視覚情報をどう解析するかをAI自身が考えられる構造**

へ変更してください。

目的はVisionモデル専用の画像認識機能を追加することではありません。

**どのLLMでも、画面という一次情報へ十分アクセスできるようにし、必要な視覚解析方法・中間表現・解析器をAI自身が考案・生成・評価できるようにすること**

が目的です。


# 1. 基本思想

SelfStructの画面取得機構を、

**Hostが備える汎用的な「目」**

として扱ってください。

この目は、

- Visionモデル
- 非Visionモデル
- Agent
- Scientist
- 将来追加される内部役割

のいずれからも、安全な範囲で利用可能にしてください。

ゲーム固有の意味はHostから与えません。

Hostが提供するのは、

**視覚情報そのものへのアクセス手段**

です。


# 2. Visionモデルを必須にしない

視覚研究機構はVisionモデル専用機能にしないでください。

## Visionモデルの場合

必要な画面・領域・Before/After等を画像入力として直接渡せるようにしてください。

## 非Visionモデルの場合

同じ視覚Evidenceへ、

- 画素値
- RGB
- 輝度
- 領域情報
- 縮小画像
- ヒストグラム
- 差分
- 形状情報
- 自作解析器の結果

などを通じてアクセスできるようにしてください。

非Visionモデルだからといって、

「画面変化量しか分からない」

状態にしてはいけません。


# 3. 「目」と「解釈」を分離する

Host側の目は、

画面を取得するだけです。

Host側から、

- プレイヤー
- 敵
- HP
- アイテム
- メニュー
- カーソル
- 文字
- 数字
- マップ
- 階段

などのゲーム意味を付与してはいけません。

意味を発見・仮説化するのはAgent / Scientistです。


# 4. 視覚情報には任意の構造が含まれる可能性があることを知らせる

LLMへの基本指示には、

以下の趣旨を含めてください。

「画面には、色、形状、模様、領域、動き、記号、数字、文字列、UI、画像その他の視覚構造が含まれる可能性があります。」

ただし、

「文字をOCRしろ」
「数字を読め」
「HUDを探せ」

など、特定の解析手段や意味を強制してはいけません。

AI自身に方法を考えさせてください。


# 5. 汎用視覚アクセスAPI

Agent / Scientistが必要に応じて視覚情報を要求できる汎用APIを設計してください。

最低限検討するもの：

- 現在画面取得
- 過去Evidence画面取得
- Before画面
- After画面
- Diff
- 任意領域Crop
- 任意サイズResize
- RGB取得
- Grayscale取得
- 原画面サイズ
- 指定座標の画素取得
- 指定領域の画素配列取得

可能な限り、

**意味を持たない低レベルな視覚アクセス**

として実装してください。


# 6. 解像度を32×32へ固定しない

現在の32×32輝度は軽量な一次特徴として残して構いません。

ただし、それを視覚情報の上限にしないでください。

Agent / Scientistが必要に応じて、

- 32×32
- 64×64
- 128×128
- 原寸Crop

などを要求可能にしてください。

全画面原寸を毎回取得するのではなく、

必要な時だけ要求する方式にしてください。


# 7. Agent自身が観測密度を決められるようにする

Agentが、

「この領域は低解像度で十分」
「この領域はもっと細かく見る必要がある」

と判断できるようにしてください。

例：

1. 全画面を低解像度で観測
2. 特定領域に変化を発見
3. その領域を高解像度で再取得
4. 必要ならさらに局所観測

という段階的観測が可能であること。


# 8. Scientistにも同じ目を与える

現在のScientistが数値経験だけを見る構造を改善してください。

Scientist自身が、

- 特定のExperienceのBeforeを見たい
- Afterを見たい
- Diffを見たい
- 一部分だけ拡大したい
- 複数Experienceを比較したい

と要求できるようにしてください。

Agentだけが画像へアクセスできて、Scientistが数値しか見られない構造を避けてください。


# 9. 追加視覚観測要求

LLMが一回のプロンプトで判断できない場合、

追加情報を要求できるようにしてください。

例：

- Experience 1052のBeforeを取得
- Experience 1052のAfterを取得
- 右上領域を128×128で取得
- Experience 1048と1052の同一領域を比較
- 現在画面を再取得

LLMが、

**「情報不足だから、もう一度見る」**

という行動を取れるようにしてください。


# 10. Vision対応モデルの場合

LLM Runtimeが画像入力へ対応している場合、

選択したEvidence画像をネイティブな画像入力として渡せるようにしてください。

ただし、

全経験画像を無条件に送らないでください。

研究目的に必要なものだけ選択してください。


# 11. 非Visionモデルの場合

非Visionモデルにも同じ視覚Evidenceへのアクセス権を与えてください。

ただし画像そのものを入力できないため、

AI自身が利用できる方法として、

- 画素配列
- 基本統計
- 差分情報
- 自作視覚解析器
- Hostが提供する汎用画像処理
- 外部ライブラリ取得要求

などを使用可能にしてください。


# 12. 汎用画像処理の基本道具

SelfStruct側で提供する基本画像処理は、

ゲーム意味を持たない汎用処理に限定してください。

例：

- Crop
- Resize
- Grayscale
- Threshold
- Blur
- Edge
- Histogram
- Difference
- Connected Components
- Template Similarity
- 色分布
- 座標変換

これらはあくまで、

**画像を調べるための道具**

です。


# 13. 固定された高機能解析を強制しない

Hostに最初から、

- OCR
- キャラクター認識
- HUD解析
- HP解析
- マップ解析

などを中心機能として組み込まないでください。

AI自身が必要性を発見して、

「文字らしい規則的な形があるため、文字認識が有効かもしれない」

などと判断した場合に、次の手段を考えられるようにしてください。


# 14. 視覚解析器をAgent自身が作成可能にする

Agent / Scientistが、

新しい視覚解析器を作成できるようにしてください。

例えば、

- 領域分割器
- パターン比較器
- 形状追跡器
- 記号分類器
- 動き解析器
- 画面状態分類器

など。

名称・構造・役割をHost側から固定する必要はありません。


# 15. 解析器の保存と再利用

AIが生成した視覚解析器は、

Agent個体の資産として保存可能にしてください。

再起動後も、

- 読み込み
- 再利用
- 改良
- 廃止
- 比較

できるようにしてください。


# 16. 解析器の評価

新しい視覚解析器を作っただけで採用しないでください。

過去Evidenceや新しい経験を使い、

- 再現性
- 安定性
- 予測への寄与
- unknown削減
- 誤認増加
- 計算コスト

などを評価してください。

有用性が確認できたものだけ継続利用してください。


# 17. 能力接続図との連携

新しく作られた視覚能力は、

能力接続図に表示できるようにしてください。

例えば実際にAgentが構成した結果、

画面取得
→ 領域分割
→ 形状比較
→ 状態分類
→ 行動選択

のような構造が生成された場合、それを人間向けに表示します。

Hostが存在しない能力を推測して表示してはいけません。


# 18. 外部ライブラリ要求

AIが、

「この問題には既存の汎用画像処理ライブラリが有効」

と判断した場合、

Hostへライブラリ取得を要求可能にしてください。

ただしAgentが直接インターネットから任意コードを取得・実行してはいけません。

既存のLibrary Acquisition Gateway思想を利用し、

- ライブラリ名
- 使用目的
- 必要理由

をHostへ要求してください。


# 19. ライブラリの安全管理

Host側で、

- 信頼元
- ライセンス
- ハッシュ
- 署名
- 対応Runtime
- Sandbox実行
- 権限制限

を確認してください。

未知のDLLや任意NativeコードをAgent本体へ直接読み込ませないでください。


# 20. OCRも「発見可能な手段」の一つとして扱う

OCRを禁止する必要はありません。

ただし初期から、

「文字があるからOCRを使え」

とは指示しないでください。

Agent / Scientistが、

視覚Evidenceから文字・数字・記号らしい構造を発見し、

OCRが有効と判断した場合に、

- 自作
- 汎用ライブラリ要求
- 外部解析器要求

などを選択可能にしてください。


# 21. Visionモデルも特権的に扱わない

Visionモデルは、

直接画像を理解できるため便利ですが、

視覚研究の唯一の方法にしないでください。

Visionモデルも非Visionモデルも、

同じEvidence ID、同じ観測要求、同じ保存構造を使用してください。

違うのは、

**画像を直接入力できるか**

だけです。


# 22. モデル能力の検出

LLM管理側で、

モデルが、

- Text only
- Vision対応

のどちらかを確認・保存してください。

Vision対応の場合は画像入力を利用可能にします。

非対応の場合は自動的に低レベル視覚アクセスや解析器経由を利用できる構造にしてください。


# 23. モデルを変えても個体の視覚能力を失わない

個体が作成した、

- 画像解析器
- 視覚仮説
- 領域情報
- 中間特徴
- 能力構造

は、使用LLMを変更しても可能な限り個体資産として保持してください。

Visionモデルから非Visionモデルへ変更したからといって、

過去に獲得した視覚能力を破棄しないでください。


# 24. Experienceと画像の対応を維持する

すべての視覚Evidenceは、

元Experience IDとの対応を保持してください。

例えば、

- Experience ID
- Before画像
- After画像
- Diff
- Crop
- 解析結果

が追跡可能であること。

仮説の根拠がどの画面だったのか後から確認可能にしてください。


# 25. 画像保存容量との両立

高解像度画像アクセスを可能にしても、

すべてのフレームを無制限に原寸保存しないでください。

既存のストレージGC方針と連携し、

重要Evidenceを優先して保存してください。

低価値な連続同一画像は整理可能にしてください。


# 26. 一時Cropの扱い

AIが調査目的で生成した大量のCropや中間画像は、

必要な根拠へ昇格したものだけ永続保存してください。

一時解析物は自動整理可能にしてください。


# 27. 視覚Observationと解釈を分けて保存する

例えば、

「右上に明るい矩形がある」

はObservation。

「これは数値表示かもしれない」

はHypothesis。

「入力後に値が減少したため状態量の可能性がある」

はInference / Hypothesis。

これらを混同しないでください。


# 28. Vision LLMの出力も事実扱いしない

Visionモデルが、

「これはHPです」
「これは敵です」

と答えても、それだけで確定Knowledgeにしないでください。

モデル出力は推論として保存し、

実際の経験・再現性によって検証してください。


# 29. Scientist Promptの変更

Scientistへの指示を、

現在の数値中心の説明から拡張してください。

最低限、

- 画面そのものが主要Evidenceである
- 必要なら追加視覚観測できる
- 色、形、配置、記号、文字等を含む可能性がある
- ゲーム意味を事前に仮定しない
- 必要な解析方法を自分で考えてよい
- 新しい画像解析器を提案・生成可能
- 情報不足なら追加観測を要求する

ことを明示してください。


# 30. WATだけに改善表現を限定しない構造を検討する

現在、Scientistの改善出力が完全WATコード中心になっています。

視覚研究が複雑化すると、

すべての画像解析器をWATだけで実装することが適切とは限りません。

安全境界を維持した上で、

Agentが、

- WAT
- Host提供の汎用画像演算
- 安全な解析Worker
- 承認済みライブラリ
- 個体Workspace内の中間データ

を組み合わせられる構造を検討してください。

ただしOS自由アクセスは与えないでください。


# 31. 視覚研究Job

Scientistが長時間の視覚解析を必要とする場合、

通常Player処理を停止させないでください。

非同期Jobとして、

- 画像比較
- 解析器生成
- Replay
- 評価

を実行してください。


# 32. 実験例

Host側へ以下の戦略を固定実装する必要はありません。

しかし、最終的にAI自身が、

1. 全画面低解像度観測
2. 安定した領域と変化領域を分離
3. 特定領域へ再観測
4. 規則的な形状を発見
5. 解析器を作成
6. 過去Evidenceへ適用
7. 新しい経験で再検証
8. 有効なら能力として採用

という研究を自発的に行える程度の自由度を目標にしてください。


# 33. GUI

研究室画面の「AI注目領域」は、

Agent / Scientistが現在要求しているCropや観測範囲と連携してください。

AIが、

画面全体
→ 右上
→ さらに小さい領域

と観測を絞った場合、人間にも分かるようにしてください。


# 34. LIVE TRACE

実際の視覚処理もLIVE TRACEへ流してください。

例：

OBS frame=10582 full 64x64
OBS crop=[1180,0,1920,280] 128x64
VISION compare evidence=10520,10582
ANALYZER create id=region_7
ANALYZER test n=128
ANALYZER promote id=region_7

ダミー表示は禁止します。


# 35. 研究ノート

視覚関連の発見も、

- Observation
- Hypothesis
- Supported
- Refuted

の区別を維持してください。

例：

観測：
「画面右上に同じ位置で変化する記号群を確認」

仮説：
「この記号群は状態変化と関連する可能性があります」

のように、人間にも事実と推測が分かる表示にしてください。


# 36. 完成条件

今回の改修後、

非Visionモデルでも、

「画面変化量だけを見る」

のではなく、

**画面という一次情報を調べる方法そのものを考えられる**

こと。

Visionモデルなら、

必要なEvidenceを直接画像として観察できること。

どちらのモデルでも、

- 観測領域を選ぶ
- 解像度を変える
- 過去Evidenceを見る
- 比較する
- 新しい解析方法を考える
- 解析器を作る
- 評価する
- 再利用する

ところまで行えることを目標にしてください。


# 37. 最終思想

SelfStructの目標は、

「Visionモデルにゲーム画面を説明させること」

ではありません。

**AIに目を与え、その目をどう使えば未知の世界を理解できるかまでAI自身に考えさせること**

です。

Hostは視覚への安全なアクセス手段を提供する。

AIは、

- どこを見るか
- 何を見るか
- どう比較するか
- どう解析するか
- どんな道具が必要か
- どの解析器を残すか

を自分で決定できるようにしてください。

Visionモデル・非Visionモデルのどちらでも、この研究ループが成立する設計を最優先してください。
