# 47. 配布方式 ― 単体実行EXE

完成版はWindows向けの単体実行可能なEXEとして配布してください。

ユーザーが開発環境を準備することを前提にしてはいけません。

通常利用において、ユーザーへ以下を要求しないでください。

- Pythonの別途インストール
- Node.jsの別途インストール
- Gitクライアントの別途インストール
- CUDA Toolkitの手動導入
- Visual Studio Build Toolsの手動導入
- ソースコードからのビルド
- コマンドプロンプト操作
- 仮想環境作成
- pipによる依存関係導入
- LLMサーバーの別途インストール
- 外部ランチャーの常用

原則として、

**EXEを取得 → 起動 → 初回設定 → LLM選択 → 必要ファイル自動取得 → 自律運転開始**

まで、このアプリケーションだけで完結させてください。


# 48. 実体は単一EXEから展開してよい

「単体実行ファイル」とは、内部処理まで物理的に1ファイルへ閉じ込めることを必須とはしません。

ユーザーへ渡す起点を1つのEXEとしてください。

必要であれば初回起動時にアプリ自身が管理する領域へ、

- Runtime
- LLM実行エンジン
- モデル
- ネイティブライブラリ
- キャッシュ
- Agent Runtime
- データベース
- 更新用ファイル

を自動展開して構いません。

ただし、これらの配置・更新・削除をユーザーへ手作業で要求しないでください。


# 49. アプリ本体の自動更新

Host本体に更新が必要になった場合、Gitベースの配布元から自動更新できるようにしてください。

通常ユーザーが、

- Git操作
- git pull
- ブランチ切り替え
- 手動ファイル置換
- 再ビルド

をする必要がない構造にしてください。


## 推奨更新方式

実行中の本体自身を直接上書きするのではなく、

1. 現在バージョン確認
2. 更新Manifest取得
3. 新版の取得
4. ハッシュまたは署名検証
5. 一時領域へ展開
6. 更新内容検証
7. Update Helperへ引き継ぎ
8. 本体終了
9. 新版へ安全に置換
10. 再起動
11. 正常起動確認
12. 失敗した場合は旧版へロールバック

という方式にしてください。


# 50. Gitはユーザーインターフェースとして見せない

内部更新元としてGitまたはGitホスティングサービスを利用して構いません。

ただし通常UIでは、

「GitのCommitをPullします」

などと表示する必要はありません。

人間には例えば、

「新しいバージョンがあります」

「更新を取得しました」

「更新後の起動確認に成功しました」

「新しいバージョンに問題があったため前の安定版へ戻しました」

のように日本語で表示してください。


# 51. 更新チャンネル

最低限、

- Stable
- Development

を分離できる構造を検討してください。

通常ユーザーはStableを使用します。

自己実験用・開発検証用にDevelopmentを選べても構いません。


# 52. 自動更新とAgent自己改造を混同しない

二種類の変更を明確に分離してください。

## Application Update

人間が開発・配布するHost、Bootstrap、GUI、セキュリティ境界などの更新。

Git経由で取得します。

## Agent Self-Modification

実行中のAI自身がAgent Root内部へ行う自己改造。

こちらはGitの公式更新とは別系統です。

Agentの自己改造によってHost本体や更新機構を書き換えられないようにしてください。


# 53. 初回起動時のLLM自動導入

このアプリケーションは外部のLLMアプリケーションを必須依存にしてはいけません。

初回起動時に、利用可能なローカルLLM候補をユーザーへ提示してください。

ユーザーは用途に合う候補を選択するだけでよいものとします。


# 54. LLM候補表示

LLM候補は技術的なモデル名だけを並べるのではなく、日本語で用途を説明してください。

例：

- 軽量・高速
- 標準
- 高精度
- コード生成重視
- 画像理解対応
- VRAM節約
- CPUでも利用可能

可能なら現在のPC環境を自動検出し、

- GPU
- VRAM
- RAM
- CPU
- 空きディスク容量

から適切な候補を推奨してください。


# 55. LLM候補をアプリへ永久ハードコードしない

モデル候補は更新可能なManifestとして管理してください。

これによりアプリ本体を更新しなくても、

- 推奨モデル追加
- 古いモデルの非推奨化
- ダウンロード先変更
- 推奨量子化変更
- 必要VRAM情報更新

を行える構造にしてください。


# 56. モデルダウンロード

ユーザーがモデルを選択した場合、

- ダウンロード
- 再開
- 完整性確認
- 保存
- 登録
- 読み込み
- 実行

までアプリ内で完結させてください。

途中でアプリやPCが終了しても、可能なら続きからダウンロードできるようにしてください。


# 57. LLM実行エンジンも内包・自動管理する

モデルファイルだけではなく、推論エンジンもアプリ自身で管理してください。

ユーザーに別途LLMサーバーを起動させることを必須としないでください。

内部的には、

- ローカル推論Runtime
- モデルローダー
- 推論Server
- GPU/CPU Backend

などを使用して構いません。

ただし通常ユーザーにはこれらを意識させないでください。


# 58. LLM Runtimeの更新

LLM実行エンジンもモデルとは別にバージョン管理してください。

新しいRuntimeを取得した場合は、

- 起動確認
- 簡単な推論試験
- 互換性確認

を行い、問題がある場合は旧Runtimeへ戻してください。


# 59. 複数LLMを利用可能にする

最終的には一つのLLMだけへ固定しない設計を推奨します。

例えば、

- 高速Player支援用
- Scientist用
- Engineer用
- コード生成用
- 画像理解用
- 日本語説明生成用

でモデルを分けられる構造にして構いません。

ただし初期状態では複雑にしすぎないでください。

単一モデルで開始し、AI自身またはシステム評価によって複数モデル使用の必要性が確認された場合に拡張できる設計にしてください。


# 60. モデル変更を自律改善対象にできる余地

将来的にはAI自身が、

「現在のモデルではこの作業の精度が不足している」

「この処理に大型モデルを使うのは非効率」

「この作業は軽量モデルで十分」

などを判断できる構造を許可してください。

ただし新しい巨大モデルの無制限ダウンロードをAIへ許可してはいけません。

ストレージ上限、モデル取得ポリシー、信頼された配布元などをHost側で管理してください。


# 61. ネットワークアクセスを二層に分離する

ネットワークアクセスは、

## Host Network

Hostが安全に管理するネットワーク処理。

用途：

- 公式アップデート確認
- モデルManifest取得
- モデルダウンロード
- 許可されたライブラリ取得
- ハッシュ・署名情報取得

## Agent Network Request

Agent自身が必要な外部資源を要求する仕組み。

AgentへOSレベルの自由なインターネットアクセスを直接与えないでください。


# 62. 外部DLL・ネイティブライブラリ利用

Agentが自己改善の過程で、

「既存のライブラリを利用すればこの処理を改善できる」

と判断することは許可して構いません。

ただし、インターネット上の任意DLLを直接ダウンロードして即座にロード・実行することは禁止してください。


# 63. Library Acquisition Gateway

外部DLLやネイティブライブラリの取得は必ずHost管理の専用Gatewayを通してください。

Agentは、

- 必要な機能
- 利用したいライブラリ候補
- 必要になった理由
- 期待する改善
- 利用方法

を要求として提出します。

Host側が安全性を確認した後にのみ取得可能としてください。


# 64. 外部ライブラリの信頼レベル

最低限、以下のような信頼レベルを持たせてください。

## Trusted

あらかじめ許可された配布元・ライブラリ。

自動取得可能。

## Verified Candidate

信頼できる配布元から取得され、ハッシュ・署名・ライセンス等を確認できた候補。

隔離テスト後に利用可能。

## Unknown

出所・完全性・安全性を十分確認できないもの。

自動実行禁止。

## Blocked

危険・不適切・ポリシー違反等の理由で利用禁止。


# 65. DLLの直接実行を避ける

外部DLLを利用する場合、可能な限りAgent本体プロセスへ直接ロードしない設計を推奨します。

別の隔離Workerプロセスでロードし、

- クラッシュ
- 異常終了
- メモリアクセス違反
- 過剰なCPU使用
- 過剰なメモリ使用

が発生してもAgent本体やHostが巻き込まれない構造にしてください。


# 66. 外部ライブラリSandbox

未知のライブラリを本番利用する前に、

1. 隔離領域へ取得
2. 完整性検証
3. メタ情報確認
4. 依存関係確認
5. Sandbox起動
6. 最小機能試験
7. リソース使用量確認
8. 異常終了確認
9. Replay Datasetを使った性能比較
10. 改善が確認された場合のみ候補昇格

という流れを通してください。


# 67. 外部ライブラリを使う目的

外部ライブラリ利用はゲーム攻略知識を得るためではありません。

許可する主な用途は、

- 画像処理
- 動画処理
- OCR
- 数値計算
- データ圧縮
- DB
- 機械学習
- GPU計算
- 高速検索
- 推論高速化
- ファイル形式処理

など、汎用的な計算能力を増やすためです。

「トルネコ攻略DLL」のようなゲーム固有知識を直接提供するものはNewbornモードでは利用禁止としてください。


# 68. 外部コードの利用履歴

外部ライブラリを採用した場合、人間向けには日本語で、

- 何のために導入したか
- どの機能を利用しているか
- どの程度改善したか
- 現在利用中か
- 廃止されたか

を確認できるようにしてください。

通常UIへDLL名や内部関数一覧を大量表示する必要はありません。

詳細名称・バージョン・ハッシュ・ライセンス・取得元は開発者詳細へ保存してください。


# 69. ライセンス管理

外部ライブラリ・モデル・Runtimeについて、

- 名称
- バージョン
- 配布元
- ライセンス
- ハッシュ
- 取得日時

を記録してください。

再配布条件に問題がある資源を、アプリ本体へ勝手に組み込まないようにしてください。


# 70. ネットから取得したものを自己改造領域と区別する

最低限、

- Host公式更新
- LLM Runtime
- LLM Model
- Trusted Library
- Agent生成コード
- Agent取得候補

を別領域で管理してください。

一つのフォルダへ無秩序に混在させないでください。


# 71. オフライン動作

初回セットアップと必要ファイル取得後は、可能な限りオフラインでも基本動作できることを目標にしてください。

ネット接続が切れたことを理由にゲームAI自体が停止しないようにしてください。

公式更新確認や新規モデル取得ができない場合は、

「現在ネットワークを利用できません。既存環境で動作を継続します。」

のように扱ってください。


# 72. ダウンロード量の暴走防止

Agent自身の判断で、

- モデル
- DLL
- ライブラリ
- Runtime

を無制限に取得できないようにしてください。

Host側で、

- 最大保存容量
- 最大同時ダウンロード
- 信頼された取得元
- ファイル種別
- 取得可能サイズ
- 重複取得防止

を管理してください。


# 73. 外部資源利用とNewborn純度

Newborn実験では特に注意してください。

汎用画像処理DLLを利用することは許可できます。

しかし、その外部資源自体にゲーム固有の意味・攻略情報・学習済み分類器が含まれている場合、Newborn実験の純度を壊す可能性があります。

そのため外部資源について、

- 汎用機能
- 学習済み汎用モデル
- ゲーム固有知識を含むもの

を区別してください。

ゲーム固有知識を含むものはNewbornでは利用禁止としてください。


# 74. 初回ユーザー体験

理想的な初回起動は以下です。

1. EXEを起動
2. 利用規約・保存先等を確認
3. PC性能を自動検出
4. 使用可能なLLM候補を日本語で提示
5. 推奨候補を表示
6. ユーザーが1つ選ぶ
7. 必要ファイルを自動ダウンロード
8. 完整性確認
9. LLM起動試験
10. 対象ゲームEXEを選択
11. ゲームウィンドウ確認
12. 入力許可キーを設定
13. 保存容量を設定
14. NewbornまたはExperienced等を選択
15. START

この後は通常、人間が継続的に設定を追加しなくても動作してください。


# 75. 最終的な配布思想

このアプリケーションは、

「ゲームAIを動かすための開発キット」

ではなく、

**一般ユーザーが一つのEXEを起動するだけで、ローカルLLMの導入から未知ゲームへの自律学習・自己改善まで開始できる完成アプリケーション**

として設計してください。

ユーザーに内部環境構築を押し付けないでください。

同時に、Agentの自由度とHostの安全境界を混同せず、

**Agentは自分自身を大胆に改善できるが、PC全体・Host・更新機構・無制限のインターネットを自由には触れない**

という境界を維持してください。
