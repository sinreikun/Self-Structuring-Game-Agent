# SelfStruct 0.7.5

Vision対応の研究LLMへ、画面を直接見るための要求方法を明示します。研究室タブには実行中のアプリのバージョンを表示します。

## 提出診断で確認したこと

0.7.4のWindows実機では、対応projectorの取得・読込、RuntimeのVision申告、GPUへの49/49層の転送が成功していました。しかし研究4 Job・40推論で画像要求・画像添付・Experiment・研究結果の提出はいずれも0件。全4 Jobが要求数上限（各24要求・10推論）で終了しました。

観測は29件成功・24件エラー・32件重複、比較は6件成功・1件重複。仮説46件はすべて未検証で、メモ4件はありましたが本文取得はありません。ゲーム側の通常Player操作と、研究LLMが目的・仮説に結び付けたExperimentは区別します。入力枠超過や新しいVision読込失敗が原因と確認した結果ではありません。

## 目的に近づけるための変更

0.7.4ではVisionが利用可能でも、共通の取得例は `output=pixels,limit=64` で、画像入力の可否は末尾のTrue/False表示でした。利用可能な画像経路をLLMが自発的に選ばない点へ対応します。

VisionをRuntimeで確認できたときだけ、画面の文字・UI・配置や目的を読み取るために `observe output=image` が利用できると明示し、共通の画素配列の例を画像要求の例へ置き換えます。pixelsは数値列、statisticsは要約であり、画像そのものを見ることと区別します。

画像・画素・統計はすべて選択可能です。実際の観測方法・領域・解像度・入力はLLMが選びます。Hostが画素要求を画像要求へ変換したり、最初から画面や履歴全文を投入したりする処理は追加しません。Text-onlyへ画像能力があるとは案内しません。主目的・研究予算・実験評価基準は変更しません。

## 実モデルでの確認と限界

提出診断と同一のGemma 4 12B Q4_K_M・context 8192で、解法を教えない合成環境を検証しました。通常の研究プロンプトと生成schemaを使い、ツールを強制せず、最初は索引だけを渡しています。LLM自身が、画像入力の例の512×512をコピーせず、対象画面に合わせた320×144のafter/before画像2枚を要求しました。両方の画像が同じJobの次の推論へ添付されたことを確認しました。

次の推論はHost計測のテキスト入力3550トークン、画像2枚、出力枠2338で、入力枠超過はありませんでした。ただしLinux CPU環境でHarnessの660秒制限に達し、2回目の推論を中断しました。Experiment・目標達成・研究結果の提出はいずれも未確認です。判定は `inconclusive_runtime_budget` で、研究ループ全体の成功とはしません。検証開始時は作業ツリーの候補だったため、実行した研究コードのハッシュが配布ソースと一致することも照合しています。

今回前進した達成条件は、利用可能な目をLLMが自発的に選び、画像Evidenceを取得する段階です。実ゲームで対象の目的を理解し、その目的に沿う操作へ進むかは更新後の実機診断で確認します。[測定記録](../evidence/v0.7.5/results.json)に成功した段階と未確認の段階を分けて保存しています。
