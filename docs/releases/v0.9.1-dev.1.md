# SelfStruct 0.9.1 — lineage-recorded-game-recovery

## 変更

ゲーム終了後の復帰を、プロセスの親子関係（系譜）の記録に基づいて行うようにしました。研究機構・予算・統計ゲートは変えていません。

- 系譜の記録：対象プロセスの選択時（GUI）と接続時（初回接続で入口が未記録の場合）に、祖先チェーン（本体 → 起動元 → ……）をスナップショットから辿って個体の設定に保存します。親が使い回し（PID リサイクル）の場合はそこで打ち切ります。
- 再起動の入口の決定：系譜のうち、共有プラットフォーム（Steam、explorer、シェル、Python 等）でなく、本体と同じディレクトリツリーに属する最上位の祖先を入口とします。該当がなければ本体自身が入口（直接起動型）です。トルネコではランチャー、直接起動のプログラムでは本体が入口になります。
- 復帰手順（attach モード）：復帰を短いスキャンの繰り返しに分解しました。各スキャンは、系譜と自ら起動した入口の子孫も候補に含めて後継プロセスを探し、ウィンドウが2回連続で安定した候補だけを採用します（自ら起動した本体は即時採用）。後継を生みうるプロセスが残っている間は起動せず、入口の起動は1回だけ、再起動間隔は指数バックオフ（5秒→60秒）です。各段階の状態はログに残ります。
- Controller の復帰ループはこの手順を呼び、状態の変化を警告ログに記録します。再接続直後の画面取得が失敗しても、復帰したばかりのプロセスを強制終了せず、手順をやり直します。

対象コミット：e700487（系譜の記録と復帰の組み替え、専用テスト8件を含む）と e665838／11f4c1c（CI 修正）。

## 実機証拠と限界

実機（トルネコ、ランチャー型）で、タイトルメニューから「ぼうけんをやめる」で終了 → 復帰を2回連続で確認しました。系譜は本体 → ランチャー → Steam の順に記録され、入口はランチャーに決まりました。復帰は1回目7.9秒、2回目6.8秒で、画面取得まで回復しました。各回の状態遷移（入口を起動 → 再起動待ち → ウィンドウなしの本体を検出 → 候補の安定待ち → 採用）がログに残っています。

直接起動型は charmap.exe で確認しました。系譜は charmap → Python → PowerShell と記録されましたが、共有プロセスで打ち切られ、入口は charmap 本体に決まりました。終了から1.2秒で復帰しました。

限界：確認は復帰手順（WindowsGame）と Controller の接続部品を直接使った監査スクリプトで行い、本番アプリの画面から通した確認ではありません。本番アプリでの稼働は、次回の診断パッケージで確認します。また、対象の選択自体は従来どおり起動中プロセスの一覧から行います。

## 配布検証

ローカル全体回帰は 395 passed / 6 failed / 3 skipped（457.79秒）でした。失敗6件は変更前の素のツリーでも同一に失敗する環境依存の既知失敗（test_process_selection の実ウィンドウ系）で、新規失敗はありません。新規の系譜・復帰テスト8件はすべて合格です。

初回 CI run 42064919473 は失敗しました。Ubuntu では系譜の入口決定が Windows パスの区切りを前提にしていたことと、起動処理が Windows 専用 API を直接使っていたこと、Windows では実ウィンドウの反復終了テストで、画面取得用の自前子プロセス（ウィンドウを持たない同じ実行ファイル）が後継と誤認されて起動が止まったことです。入口決定を区切り文字に依存しない実装に変え、起動処理を分離し、自プロセスの子孫は（自ら起動した入口の系統を除き）起動の妨げに数えないよう修正して、タグを付け替えました。

2回目の CI run 42068521293 では Ubuntu は通過しましたが、Windows の同じテストが再び止まりました。系譜にもホスト（テスト実行プロセス）が含まれるため、その子である画面取得ワーカが子孫台帳に入り、「起動した系統」への例外がワーカにも及んでいたことが原因でした。例外を、自ら起動した入口の系統だけに限定しました（回帰テストを追加）。
