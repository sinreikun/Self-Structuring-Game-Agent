# 複数ステップの研究（0.6.0）

研究LLMは同じJobの中で `actions` を返し、Hostが実行した結果を受けて再推論します。観測対象・領域・処理・入力の選択はLLMの判断です。ゲーム名、攻略知識、文字認識の意味ラベルはHostから与えません。従来の `visual_requests` も引き続き受け付けます。

## 操作とフェーズ

応答は `findings / actions / problem / reason / wat` のJSONです。`findings` の任意の `id`（例 `h1`）を、同じJobの後の実験・評価で参照できます。Hostが実際のKnowledge IDを返します。

- Observation/Hypothesis：何が分かったか、不明点、次に調べるEvidenceと実験を判断。WAT本文・ABIを一律に要求しません。
- Experiment planning/Experiment：明示的な許可入力計画をPlayerへ渡し、Before/Afterと完了・中断を受け取ります。
- Evaluation：仮説の事前登録確率と、実験で取得した画面変化を比較します。
- Analyzer creation：既存の安全な視覚演算を定義・試験・独立評価します。
- Candidate implementation：`candidate` で根拠Evidence、問題、必要挙動、評価条件を指定した後、現在の実装とABIを渡します。
- Repair：保存された候補と構文・ABI・評価エラーを渡し、世界理解や新仮説を同時に要求しません。

旧応答の直接 `wat` 提出も互換性のため受理します。既存の隔離事前検査・有限修正・Replay・回帰比較・実入力比較を通るまで採用しません。解析器も定義だけではcandidateのままです。定数0/0.5/1、過去頻度、現行Agentとの比較基準を緩めません。

## 観測・比較・解析

```json
{"actions":[{"op":"observe","event":10582,"phase":"before","box":[1040,0,1600,320],"size":[128,64],"mode":"RGB","output":"pixels","limit":128}],"findings":[],"wat":""}
```

`phase` はbefore/after/diff。event省略は現在画面、`fresh:true` はPlayerの新しい取得を待ちます。返ったobservation IDで同じ画面を再取得できます。boxは原画像座標、sizeは変換後サイズで、両者を取り違えません。

`compare` は同じ指定へ `compare:{event,phase,box}` を追加します。`analyze` は `operations` にgrayscale/threshold/blur/edge/invertを指定します。pixelsはoffset/limitでページ取得でき、statistics/histogram/componentsでも解析できます。画像上の意味は自動で確定しません。

Vision能力をRuntimeで確認できた場合、要求したoutput=imageだけを画像添付します。Text-onlyでは同じEvidenceを画素や数値で返します。最初の小さなBefore/After概観は、予測誤り・変化量・新しさで優先した1 Experienceだけです。全Experienceを画像で無条件投入しません。

`analyzer_create / analyzer_run / analyzer_evaluate / analyzer_list / analyzer_get / analyzer_retire / evidence_keep` もactions内で使用できます。独立経験を用いる解析器の昇格条件と資源取得の境界は従来通りです。

## 実験と仮説

```json
{
  "findings":[{"id":"h1","text":"入力4の後に画面が変化する確率を検証する。意味は不明。","evidence":[10582],"action":4,"change_probability":0.8}],
  "actions":[{"op":"experiment","hypothesis":"h1","action":4,"duration":60,"wait":100,"repeat":8}],
  "wat":""
}
```

actionは0始まりで、ロード中の個体の許可キーだけです。durationは10..500ms、waitは10..2000ms、repeatは1..8。1 Jobにつき最大4計画・32入力です。Scientistから直接ゲーム入力せず、唯一のPlayer入力スレッドが通常探索の代わりに実行します。候補の実入力比較・試用世代とは混在させません。

`condition:{box,size,mode,operations,mean_min,mean_max,max_wait_steps}` で、変換画像の画素平均が指定範囲となるまで待てます。max_wait_stepsは1..128（既定32）。これは汎用の数値条件で、ゲーム状態の意味判定ではありません。条件成立時にも画面が操作前に変化する可能性があり、因果関係の証明ではありません。

PAUSE中には入力しません。待ち時間上限120秒で期限終了できます。STOP・PAUSE中断・再起動で途中入力を再送しません。実験IDと送信済みExperience IDを永続化し、同じJobの復帰で二重実行しません。未完了経験は学習に使いません。中断した実験は部分完了数と理由を残します。

同じ入力を再試行する明示的Experimentは新しい経験を得るため重複観測とは区別し、上記の有限予算内で実行します。

`evaluate` では仮説IDとchange_probabilityを指定します。仮説作成時のaction/change_probabilityと一致し、同じ許可入力の完了経験が16件以上ある場合だけWilson 95%区間で支持／反証を記録します。事後に確率を選び直すこと、異なる入力の混在、少数例、条件付き実験から無条件仮説を結論することは判定不能です。自然言語の意味仮説や因果関係を確定扱いしません。未検証・検証中・支持・反証・判定不能を研究ノートで区別します。

## 停滞・予算・保存

「確認したい」などの意図だけが残る応答、または具体的行動のない研究が複数続く場合、未実行・未検証であることをLLMへ伝え、具体的actionsを同じJobで再要求します。Hostが自然文から勝手に領域やキーを決めることはありません。再誘導後も行動がなければ停滞と記録し、失敗を隠して実験成功と表示しません。観測・仮説だけで十分な研究は正当な完了です。

同じ過去Evidence・領域・解像度・処理は実行済み結果を参照して重複と記録します。新しいfresh観測や有限の反復実験は別です。1 Job最大10 LLM呼出し・24要求・600秒・画像添付合計4MiB。時間はステップ間にも確認し、実行中の単一推論や入力は既存のタイムアウト／中断境界に従います。再起動で予算をリセットしません。上限時は既に取得した根拠・仮説・結果を保存して終了します。

新しいEvidence・仮説・評価・実験・解析方法・実装候補、独立評価で実測したunknown削減をJobへ記録します。実測していないunknown削減はnullです。行動変更の実入力比較では各群の視覚ハッシュ種類数、観測時間当たりの種類数、変化数、同一状態／入力の反復数も記録します。これは観測指標で、ゲーム進行や因果効果を保証せず、予測評価の採用条件を緩めません。

一時Cropはファイルへ保存しません。要求元の原画像を参照し、Job中だけpinし、終了時に解放します。根拠Knowledge・Experimentに使ったイベントやevidence_keepで明示保護した観測は保持します。画像base64はJob・診断へ保存しません。

## Windows実機での確認手順

1. アプリを閉じ、既存Launcher 1.1.0を起動して0.6.0へ更新します。個体をロードし、許可キーを確認してSTARTします。新生個体へのリセットは不要です。
2. 研究開始後、LIVE TRACEの `RESEARCH ... job=... step=...`、`OBS` のExperience・crop・解像度、`result` と次の `resume` を確認します。現在研究欄にも実行中の処理を表示します。
3. 研究ノートの「研究履歴」で同じJobのaction_history／research_stepsを見ます。「実験」「検証中」「支持」「反証」「判定不能」でも記録を確認できます。解析器候補は能力接続図へ反映されます。
4. `EXPERIMENT queued/execute/complete` が発生したら、job・hypothesis・入力番号・repeat・イベントIDが対応するか確認します。PAUSEで実験入力が止まり、STARTで継続可能か確認します。既に中断した入力を再送しないため、実験が中断終了することは正常です。
5. 数件の研究が終わった時、または停滞・エラーが見えた時に、できればSTOP前に「診断ZIPをコピー」を押して提出してください。PAUSE中でも採取できます。採取によって状態は変更しません。

ZIPにはjobsの `research_steps`（開始・完了時刻、消費したaction_id、画像数）、`action_history`（要求、実行／重複／エラー、結果返却時刻、Evidence、領域、解像度）、`progress`、停滞・上限を含めます。`research_experiments` は要求Job・仮説・入力計画・送信イベント・Before/After参照・結果を含みます。Candidateのハッシュ、解析器の定義・評価、仮説の検証状態も追跡できます。中断中なら完了時刻がないことをそのまま残します。Prompt・候補ソース全文・画素配列・画像添付のbase64は診断へ出しません。

確認結果は「機構が動いたか」と「実ゲームで有効だったか」を分けます。LLMが適切な要求・解析器・実装を生成しない可能性は残るため、診断の実記録で判定します。

## 今回の自動検証の範囲

Text-onlyとVision対応クライアントを想定した決定論的LLM Harnessで、実画像と実際のPlayer入力経路を通じ、Crop→比較→再推論→反復Experiment→仮説の統計評価→解析器候補生成を同じJobで検証します。Visionでは要求画像が次の推論へ添付され、Text-onlyでは画素・統計が返されることを確認します。これは外部モデルが自律的に同じ判断をする証明ではありません。

CIでは既存の実モデル推論・研究も実行し、実際のactions数・再推論・停滞・上限を推論検証レポートへ残します。0.5.2の提出ZIPは読み取り専用で元画像のハッシュ、領域・RGB・エッジ・画素・統計・ヒストグラム・Components、有限修正とPAUSE状態を再確認します。実ゲームの最終確認は利用者のWindows実機で実行し、返送ZIPで確認します。


## 0.6.1：要求形式と研究JSON修正

実機診断で、モデルが `op` 文字列へevent・box等のJSONを丸ごと書き込む問題を確認しました。操作ごとにopの列挙値、パラメータ名・型・必須項目を定義し、RuntimeのJSON SchemaとHost検査で共用します。キー番号は現在個体の範囲、findingsのEvidenceはそのJobで提示したExperience IDに制約します。observation IDとは区別します。文字列内の擬似コマンドを推測して実行することはしません。

途中JSON・不正なEvidence参照等の形式修正はprotocol_repairとして扱い、観測結果・許可IDを保ったまま修正します。新しい正しいactionsを実行でき、正しい応答の後は修正状態を解除します。WATを生成するよう要求するのは、実際の候補を保持しているimplementation修正だけです。両者とも有限の修正予算を維持します。

CIでは通常の自律研究結果とは別に、実モデルへ観測APIの形式確認を明示的に依頼する接続テストを追加します。モデルが生成した型付きobserveを実行し、その結果を同じJobの次の実モデル推論へ渡します。これは自律的に観測・実験を選ぶ能力の証明ではありません。実ゲームでの最終判定は引き続き診断ZIPで行います。

PAUSEはゲーム入力の休止です。LLM研究も止めたい場合はSTOPを使用してください。0.6.0の09:50→09:52の実機診断では経験数が26,225のまま変化せず、未送信の中断経験で止まった一方、LLMは同じJobを8回の推論と有限修正で終了しました。


## 0.6.2：実験と仮説の接続・研究コンテキスト

0.6.1の実機診断では、追加観測・比較→同じJobで再推論→Experimentまで実行できました。診断収録分で27実験／84入力が完了しましたが、すべて仮説IDがnullで、支持・反証の評価へ接続されていませんでした。

新しい研究応答はfindings.idを必須とし、Experimentにはhypothesis（findings.idまたは既存Knowledge ID）を必須にします。Hostが文章から仮説を推測して紐付けることはありません。新しい主張へ以前のidを再利用せず、新しいidを付けます。旧版の未接続実験はそのまま保存し、遡って支持・反証や結び付きを捏造しません。

conditionは入力を行う状態の選別条件です。解像度・modeだけでは条件にならず、mean_min/mean_maxの少なくとも1つが必要です。無条件ならcondition自体を省略します。画素値の全域0..255を許す条件は状態を選別しないため、評価上も無条件として扱います。狭い範囲の条件から無条件の変化確率を結論しない制限は維持します。少数例・未登録の確率・異なる入力の混在も判定不能です。

画像参照のevent／observation／freshは互いに両立する組合せだけをJSON Schemaで許可します。比較先も同じ制約を適用します。

モデルへは直近8件の視覚結果を渡し、うち古い4件はID・領域・解像度等の参照へ縮約します。直近4件の研究アクション結果と既存の配列縮約も併用します。原結果・全要求・画像ハッシュはJobの永続記録へ残し、必要なら同じ参照を再要求してキャッシュ結果を確認できます。省略を明記し、統計や意味をでっち上げません。診断にはcontext_compactionsを残します。入力枠がなお不足する場合は、従来どおり成果を保存して上限終了します。

実機確認では、研究履歴にhypothesesの別名とKnowledge ID、Experiment.hypothesis、結果返却後のevaluateが対応するか確認してください。仮説の支持・反証や解析器・候補の採用は実記録で判定し、実験回数だけで成功扱いにはしません。

再推論には仮説の別名とIDだけでなく、参照中の保存済み主張・検証状態・事前登録した入力と確率も渡します。長い本文は省略を明記した抜粋とし、原文は個体の研究ノートへ保持します。実験結果から評価対象の主張を見失わないための記録です。


## 0.6.3：仮説IDの再利用と事前登録の保護

0.6.2の実機診断では仮説に接続したExperiment 15件・33入力とevaluate 2件を確認しました。評価は未登録の確率かつ経験1件／2件のため判定不能でした。複数のJobでは、モデルがh1等を変更した主張へ使い回して研究を中断していました。

新しい応答では推論ステップごとに未使用のID候補（r1_1等）を提示し、Schemaでも新規findings.idをその候補へ限定します。既存仮説を試すだけならfindingsを空にし、actions.hypothesisへ既存の別名／Knowledge IDを指定します。主張や登録する確率を変更する場合は新しいIDと新しい経験が必要です。Hostは仮説の内容や実験入力を選びません。

Hostは同一応答のすべての仮説参照を、保存前に検査します。不正なID再利用を拒否しても、途中までの仮説・claimが増えません。同じ主張・同じ登録内容の既存IDには新しいEvidenceを追加できます。文章・根拠が同一でも登録する確率が違う場合は、独立した新しいclaimとして区別します。新しいclaimの評価開始点は、登録時点で既に存在する最新イベント以後です。既存結果を見てから選んだ確率を、過去の経験へ遡って検証しません。

判定不能の評価結果には、未登録・確率不一致・入力不一致・条件による選別・標本不足等の理由と、必要な16件という基準を返します。未登録の場合は、先に新しい仮説のactionとchange_probabilityを登録し、その後に実験する必要があります。過去の実験を新しい目標へ移し替えません。

同じキャッシュ済み結果だけを2ステップ続けて要求した場合、次の推論へ重複とページ取得の説明を返します。同じpixelsを再要求しても範囲は増えず、next_offsetがある場合はoffsetで別の区間を取得できます。観測先や解析方法は引き続きLLMが選び、通常の予算上限を維持します。診断には発行した新規ID候補と重複再誘導の回数を残します。


## 0.6.4：実験した仮説を評価まで参照する

0.6.3の実機診断では、新規4 JobにID再利用エラーはなく、仮説に接続した10実験・26入力が完了していました。しかし観測が続くと、実験した10個の対象のうち9個が最後のhypothesis_contextから外れていました。元データはDBへ保存されていても、推論に必要な実験対象を見失う問題でした。

Job内で実験した仮説（最大4計画の対象）を、直近の要求や最新仮説より優先して参照欄に保持します。本文の抜粋、別名とKnowledge ID、検証状態、事前登録した入力・確率を引き続き渡します。観測を続けたり新しい仮説が増えたりしても、実験済み対象を直近表示から落としません。

experiment_contextには、そのJob内の実験ID・対象仮説・状態・要求回数・完了回数・完了Evidence ID・画像変化あり／なしの件数を記録します。仮説ごとの集計では重複しない完了イベントだけを数え、異なる仮説を混ぜません。scope=current_jobであることを明示し、仮説全履歴の評価結果とは区別します。計画数上限4、要求入力上限32、使用数と残数も渡します。期限切れ・中断・未送信は完了に数えません。

これは実記録の要約で、支持・反証や成功判定を代行するものではありません。LLMが次の観測・実験・evaluate・解析器・候補を選びます。未登録の確率、少数例、異なる入力や選別条件を混ぜた推定を、支持と断定しない制限は維持します。診断の研究履歴にも同じ実験集計を残し、実験→再推論→評価の対象が対応しているか確認できます。

### 0.6.5: 実験数と評価条件の区別

`experiment_context.hypotheses[].by_action`は現在Jobの入力別完了数・画像変化数です。`evaluation_requirements`には事前登録の有無と対象、同じ登録入力で登録後に完了した数、不足数、未登録・条件選別・入力不一致などの阻害理由を返します。`scope=current_job_only`であり、これは統計評価の実行や支持・反証を意味しません。明示的なevaluateでは同じ仮説の全Jobを従来どおり再検査します。未登録の結果を後から有効な標本へ変換しません。

終了時には上限判定より先に実験・仮説集計を更新し、最後の実験が診断集計から欠けないようにしています。上限後に追加LLM推論や追加入力は実行しません。

### 0.6.6: 実験履歴を含めた入力枠の制御

Jobのexperiment_contextは詳細を保持し、モデルにはexperiment_prompt_contextで重複を省いた台帳を返します。入力枠が不足する場合、最近のアクション履歴と別名を圧縮し、古い視覚配列・結果を省略します。現在Jobで実験した仮説の主張と事前登録、入力別内訳と評価条件を保持します。最新の実画素／画像を優先し、最新画素を64値へ制限する場合は元の値と次offsetを明示します。保存済みvisual_historyとaction_historyは変更しません。

context_budgetにはモデルtokenizerのinput_count、context、reserved_output、output_budget、image_count、compact_history、omitted_visual_results、omitted_attachmentsを保存し、診断ZIPへ含めます。出力目標は可能なら2048、最新Vision画像を保持しても最低512の出力枠が確保できるなら画像を残します。不可約の入力も収まらない場合は既存のinput_budget_exceededで有限に保存終了します。

### 0.7.0: 主目的・副目的と取得式の外部記憶

主目的は研究対象の仕組みと目的を理解し、その目的に沿って操作することです。副目的は人間向け研究結果の作成です。画面変化や予測損失を目的そのものへ代入しません。`research_mission.MISSION`が情報源・手段・権限・役割を説明し、Jobと診断に方針の版を保存します。

初回は3件の経験メタデータと小さい索引を渡し、ScientistによるBefore/Afterの自動先読みを行いません。元のGame/Playerの経験収集は継続します。`memory_search(collection,query/ref,cursor,watermark)`で索引を調べ、`memory_read(collection,ref,revision,offset,limit)`で本文を取得します。limitは最大1600文字です。正本の版と選択版を照合し、検索した版のスナップショットを同じJob内で最大32件・各64KiBまで保持します。本文ページは選択版で返し、正本が更新されればsource_changed/source_revisionで明示します。保持されていない旧版の要求はstaleと現在の版を返します。完了Jobの読取スナップショットは次回保存時に解放します。検索watermarkは挿入の上限を固定するもので、全記録の更新を凍結するスナップショットではありません。本文ページは必ず同じ版で取得してください。

保存領域はexperience/knowledge/experiment/visual/research/note/reportです。各領域は個体内の既存正本または専用テーブルを使い、任意ファイルやSQLを実行しません。取得した完了経験は同じJobの根拠IDとして登録・保護します。削除済みの記録はunavailableとし、内容を補完しません。

`memory_note`は短い課題・計画・不明点を保存します。既存メモの更新にはrefとrevisionを使い、古い版での更新を拒否します。`research_report`は対象の目的、goal_status、根拠、観測記述・仮説、未確認事項、次の方針を保存し、GUI「研究結果」と診断内の研究結果.mdから読めます。メモ・報告は仮説の支持・反証や候補採用を自動変更しません。

実機確認では、(1)初回のLLMが索引から何を検索・取得したか、(2)実際に要求した目・領域・解像度、(3)結果が同じJobへ返ったか、(4)対象の目的を何と考え根拠をどう記したか、(5)目的に沿う操作・実験へ進んだか、(6)研究結果と未確認事項を人間向けに残したかを確認します。memory_*のref/revision/offset/content_sha256、研究stepsのconsumed_actions、実験イベント、mission、context_budget、研究メモ・研究結果を診断ZIPで追跡できます。レポート未提出や目的不明もそのまま記録し、達成扱いしません。
